# 天涯明月刀 · 养成数值与战斗模拟系统

> 一个自研的 MMORPG 养成数值分析工具 —— 把游戏内的养成规则**逆向建模为可计算的代码**，用于量化属性收益、优化升级路径、模拟战斗结果。
>
> **性质**：个人项目，**持续迭代中**（2026.03 起）
> **用途**：求职作品展示（游戏数值策划方向）
> **本仓**：只放说明，不放源码（见文末「关于源码」）

---

## 为什么做这个

玩《天涯明月刀》的过程中，我逐渐意识到一个问题：**玩家面对的其实是一个多变量优化问题**。

游戏里有 11 个并行的养成系统（神兵、灵势、经脉、小师妹、心法、琅纹、镇派、经纬棋盘、文心、伙伴、装备），每个系统都有自己的成长曲线、边际收益和资源成本。玩家有限的资源应该往哪个系统投、投到什么程度，直接决定了角色强度的效率。

但游戏本身不提供任何量化工具——玩家只能靠经验和攻略帖。于是我决定自己写一个：**把每个系统的数值规则从游戏里「读」出来，变成代码里的模型，再让求解器给出最优路径。**

这个项目也是我对"数值策划"这件事的最初兴趣来源。

---

## 项目能做什么

### 1. 角色属性建模
把 11 个养成系统的数值规则统一建模，输入你的养成进度，输出完整角色属性模型（`CharacterAttributes`）。

### 2. 门派转换与 Buff 层
- **门派转换**：不同门派有各自的属性修正与技能加成
- **Buff 增益层**：支持 **43 条 Buff（4 大类：食物 / 门派主动 / 门派被动 / 组队阵法）**，处理叠加、互斥、优先级与生效顺序

### 3. 战斗公式计算
从属性模型出发，经战斗公式层换算为**功力 / 战力 / 伤害**等可比较的指标。含 **PVE（vs Boss：命中 / 会心 / 会伤 / DPS）** 与 **PVP（定力 / 破招 / 拆招）** 两套对决模型。

### 4. 优化求解
- **升级 ROI 排序**：在当前进度下，各养成系统的下一单位投入分别能带来多少收益
- **路径规划**：给定资源约束，给出推荐的养成顺序
- **跨系统分析**：瓶颈检测与优先级分组

### 5. GUI 与数据管线
- **桌面端 GUI**（FastAPI + 原生 JS），可交互式查看与调整；含多档案管理、图形化编辑器、配置版本回滚
- **决策工作台**：把建议组织为「当前状态 → 筛选条件 → 决策卡 → 备选方案 → 结果可信度」五区，每个结论标注可信度状态（现算 / 过期 / 缺失）
- **截图数据管线**：通过多模态视觉模型 API，把游戏内截图自动解析为结构化数据，减少手工录入

## 架构设计

分层架构，**规则与代码严格分离**——游戏规则以文档形式沉淀在 Knowledge 层，代码只负责计算：

```
Knowledge（规则文档：游戏机制、公式来源）
    ↓
Domain（11 个养成系统模块，各自独立建模）
    ↓
Buff（增益层：43 条 Buff，处理叠加/互斥/优先级）
    ↓
Formula（门派转换 + 战斗公式）
    ↓
Agent / Solver（推理层 + 优化求解）
    ↓
App（GUI / 命令行 / 桌面打包）
```

**这样分层的好处**：游戏版本更新时，只需修改 Knowledge 与对应的 Domain 模块，上层计算逻辑完全不动。

→ 更细的分层边界、数据流与设计取舍见 [`说明.md`](说明.md)。

## 工程规模与治理

| 指标 | 数据 |
|---|---|
| 核心代码 | `src/` 约 **6.3 万行**，**124 个 Python 模块** |
| 测试代码 | 约 **6.2 万行**，**210+ 个测试文件** |
| 架构决策记录 | **31 条 ADR**（记录每次关键设计取舍与原因） |
| 工程约束 | 提交门禁（单元测试 + 真浏览器端到端 + 审计）+ 数值金标锚回归 |
| 自动化 | 18 个 Skill + 审查 / 推理 Agent（辅助规则校验与跨系统分析） |

> 代码量与测试量接近 1:1——这是为了保证数值计算的正确性：**数值错误会直接导致结论错误**，所以每个模块都有对应的测试覆盖。
>
> 数值金标锚：冻结一份标准 11 系统配置，每次提交都「现算一遍」与冻结值逐项比对，任何数值回归立即失败。项目至今累计冻结 **100+ 次**可复现验证锚。
